# ADR-002: 登录架构 —— 原生表单 + 图形验证码（放弃 WebView 方案）

## 状态

已接受

## 背景

需要让 App 获取广州软件学院教务数据（课表/考试/成绩）。
认证链路为：CAS 统一身份认证（LYUAP）→ ehall 办事大厅 → 正方教务系统。

实测结论（2026-09-18）：

| 项 | 实测结果 |
|---|---|
| 认证系统 | LYUAP（联奕），Vue SPA，登录页仅 4917 字节 + 压缩 JS |
| 验证码接口 | `GET https://cas.gzus.edu.cn/lyuapServer/kaptcha` → 200 |
| 验证码格式 | `{"kaptchaType":"1","uid":"<32hex>","content":"data:image/png;base64,..."}` |
| 验证码类型 | **普通图形验证码**（kaptchaType=1），100×25 PNG，已成功解码验证 |
| 教务系统 | 正方（`/jwglxt/xtgl/login_slogin.html` 为正方标志路径） |
| DNS | 双解析：校内 172.16.3.x / 校外 110.64.203.221-223（公网可达） |
| 站点 | 全部直连可达，无 CDN，nginx/1.27.0 |

## 决策

**采用原生登录表单 + 用户手动输入图形验证码。**

登录流程：

1. App 启动/登录页加载 → `GET /lyuapServer/kaptcha` 取验证码
2. 解析 JSON，取 `uid`（提交时回传）与 `content`（base64 PNG）
3. `Base64.decode` → `BitmapFactory` → 显示在 `ImageView`
4. 用户输入 学号 + 密码 + 验证码
5. POST 登录（参数格式待从 app.js 逆向确认）
6. 成功后持有 Cookie（JSESSIONID / CASTGC），后续调教务接口复用

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **原生表单 + 手动验证码** | 验证码由人识别，100% 可靠；无 JS 逆向负担；UI 全原生流畅；无第三方依赖 | 需逆向登录参数格式 | ✅ **采纳** |
| WebView 内嵌 CAS 登录 | 免逆向，天然过验证码 | 体验割裂；CAS 页面为桌面版未适配移动端；Cookie 提取时机脆弱；UI 无法原生 | ❌ 体验差 |
| 打码平台自动识别 | 全自动 | 违规、收费、不稳定；识别失败率高；教务升级即废 | ❌ 明确否决 |
| 逆向 LYUAP 密码加密算法 | 可免验证码登录 | 加密算法在压缩 JS 中，升级即失效；且仍需过验证码 | ❌ 收益为负 |

**关键论证：验证码是"人机验证"，它的设计目的就是阻止自动化。**
让用户手动输入是**唯一既合规又稳定**的方案，且成本极低（用户本来就是本人操作）。

## 影响

**变容易：**
- 无需逆向 LYUAP 的密码加密逻辑（只可能需 MD5/RSA，待确认）
- 无需处理 WebView Cookie 同步、JS 桥接
- UI 完全原生，Material 3
- 不依赖任何第三方打码服务

**变难 / 需注意：**
- 必须逆向登录 POST 的**参数名与格式**（下一步：分析 app.js，272KB）
- 密码若前端 RSA 加密，需在 Kotlin 中实现同一算法（公钥可从 JS 中提取）
- Cookie 会过期 → 需实现"登录态失效 → 引导重新登录"流程
- **不在 App 内存储明文密码**（安全红线）；如要"记住密码"须用 EncryptedSharedPreferences

**安全约束（必须遵守）：**
1. 密码绝不落盘为明文；如实现自动登录，用 `androidx.security:security-crypto`
2. 全链路 HTTPS，禁止明文 HTTP 降级
3. 不在日志中输出账号/密码/验证码
4. 不在 App 内绕过任何验证码机制
